## 2. ACCESSDB.BIN（FDB, File Data Base）格式

游戏启动时 `Eve_FDBInitial`（**0x13D230**）把 `dat_load2` 读入的 ACCESSDB.BIN
前 **60 个 u32** 依序搬进各全局数组。**section 下标连续，但目标数组槽位有跳跃**：

| section 下标 | 目标 | 内容 |
|---|---|---|
| 0..7   | BG_SctDB[0,1,2,3,4,5,**8,9**] | BG000..BG900 的记录表（槽 6/7 跳过） |
| 8..16  | CBD_SctDB[0..8]   | CBD000..800 记录表 |
| 17..24 | VOC_SctDB[0..7]   | VOC000..700 记录表 |
| 25..33 | SCR_SctDB[0..8]   | SCR 记录表（scn.py 的 `Fdb.scr_entries` 用 `25+group`） |
| 34..41 | BG_NoDB[0,1,2,3,4,5,8,9] | BG 编号→记录号映射（u16 表） |
| 42..50 | CBD_NoDB[0..8]    | |
| 51..59 | EVE_NoDB[0..8]    | 脚本事件号映射（scn.py 的 `eve_map` 用 `51+group`） |

- 记录表 = `(u32 sector, u32 size)` 对，单位**扇区（0x800）**，相对 BIN 文件头。
- `size==0` 为空记录。加载：`Eve_BGRead`（0x13D450）→ `dat_load3`（0x11AC50）→ 整条
  记录 DMA 到 `0x1700000 + 槽*0x80000`。**记录不能超过 0x80000 字节**
  （原始数据最大 0x7D800，紧贴上限）。
- BG 编号→记录号：`Eve_GetBGRealNo`（0x13D0A0）：
  `BG_NoDB[no/10000]` 指向 u16 表，`real = 表[(no/100)%100] + no%100 - 1`。
- 数值验证：section 0..7 的记录表按扇区累加正好等于 BG000..BG900 八个文件的大小
  （BG200 例外：表声称比文件多 101 扇区的虚报尾部，对应的 #542 是废记录，
  解不出来，游戏也未引用；工具对它原样拷贝）。

### ⚠️ 旧工具的历史 bug（已由 KitaAccess 修复，此处留档防复发）

旧 `tools/legacy/bg.py` 把 BG800/BG900 映射到 section **8/9**——那其实是
CBD000/CBD100 的表。正确映射是 section **6/7**（section 连续使用，跳过的是
数组槽位不是 section）。后果：旧 png/BG800、png/BG900 全是错的/空的。

## 3. BG 记录 / 图片格式

### 3.1 容器

```
记录 blob（扇区对齐）:
  +0x00 u32 块0压缩流偏移（恒 0x10）
  +0x04 u32 块1压缩流偏移（单块记录为 0）
  （0x10 字节表头，不足补 0；picbg_decode_task 只用前 2 项）
  +0x10 块0 LZSS 流, 块1 LZSS 流 ...
```

每条记录最多 2 块（对应上下两块 512KB 纹理）；2275 条有效记录中 2203 条 2 块、
71 条 1 块、1 条废数据（BG200 #542，表项是随机数，解析失败按原样拷贝）。

### 3.2 LZSS 压缩流（decode **0x11A5A0** / decode_task **0x11A7F0**）

协作式解压器：`decode(src,dst,0x100000)` 只登记状态，`decode_task()` 每帧泵一段。
格式：

- 控制字节管理 8 个操作位，**LSB 在前**；每组 = 1 控制字节 + 8 个操作的数据。
- 位=0：字面量 1 字节。
- 位=1：读 token
  - `0x00..0x7F` 长匹配：`len=(t>>2)+3`（3..34），再读 1 字节，
    `dist=((t&3)<<8)|b`（**直接距离，1..1023**；`dist==0` 游戏会跳过拷贝但仍消耗控制位）
  - `0x80..0xBF` 短匹配：`len=((t>>4)&3)+2`（2..5），`dist=(t&0xF)+1`（1..16，**距离-1 编码**）
  - `0xC0..0xFE` 字面量串：`(t&0x3F)+8`（**8..70**，71 会撞 0xFF 结束符）字节原文
  - `0xFF` 结束：输出补零到偶数字节后返回
- `decode` 的 max 参数是 0x100000（1MB）。

注意长/短匹配的距离编码不一致：长匹配直接编码、短匹配是距离-1，都是游戏代码原样。

### 3.3 解压后的块（`tex_load` **0x11B6A0** 解析；`BG_Set` 0x124490 / `picbg_get_size` 0x13CAB0）

```
块（≤0x100000）:
  +0x00 u32 = 0x13（实测恒定；非 0 = 256 色调色板）
  +0x04 u32 = 1
  +0x08 u32 调色板偏移（相对块首）
  +0x0C u32 部件数
  +0x10 u32[] 部件偏移表
  调色板 @+0x08: 256 项 × 4B = R,G,B,A（GS RGBA32 内存序，A ∈ 0..0x80 半程）
```

**部件**（头 0x70 字节，本质是游戏内欲 DMA 的 GIF 包模板，加载时只 patch 少数字段）：

| 偏移 | 含义 |
|---|---|
| +0x24/+0x26 | u16×2，TEX 相关字段（BG 数据里为 0） |
| +0x30 | u16 宽（== +0x64） |
| +0x32 | u16 = 0 |
| +0x34 | u16 高（== +0x66；tex_load 另按 `&0xFFF` 用作 VRAM 行进） |
| +0x60 | u32 像素字节数 = w*h |
| +0x68 | u8 像素二次压缩标志（**BG 数据全为 0**） |
| +0x69 | u8 二次压缩模式（`>>3==1`：单字节 RLE；否则 4 字节节距 LZ——仅系统图用，BG 未用） |
| +0x70 | 像素：w*h 字节调色板索引；同块多个部件纵向堆叠 |

典型 BG：640×448 = 部件0 640×409 + 部件1 640×39，两块各 ≤512KB。

### 3.4 调色板 swizzle（已实证）

文件内 256 项是 **GS CSM1 顺序**（索引 bit3↔bit4 互换，自逆）：
`文件索引 f 的颜色属于逻辑索引 (f&0xE7)|((f&8)<<1)|((f&16)>>1)`。
调色板上传链 `tex_load → pal_w → pal_set(0x11C240)` 全程 1:1 拷贝，无交换，
即 swizzle 靠"文件里预先排好"实现。验证：两种顺序各渲染一张 PNG，
反 swizzle 的相邻像素色差只有原始顺序的一半，人眼确认无色噪。
alpha：文件 0..0x80 ↔ PNG 0..255，`a*255/128` 与 `a*128/255`（四舍五入）互逆。

## 4. KitaAccess（tools/KitaAccess，.NET 8 + ImageSharp）

```
KitaAccess d <data_dir> <out_dir>            解包：BG*.BIN → PNG + list.xml
KitaAccess e <data_dir> <work_dir> <out_dir> 打包：只重建改动过的记录
KitaAccess t <data_dir>                      自测：全块重压缩+回读比对
```

- `d` 读一次 ACCESSDB 覆盖全部档案（这就是"Python 每个脚本重读 ACCESSDB"痛点的解法）；
  记录级并行；废记录/空记录跳过。输出 `<out>/BGxxx/RRRR_B.png` + `<out>/list.xml`
  （含每个 PNG 的 sha256）。
- `e` 以 list.xml 的 sha256 检测改动：**无改动的文件一个字节都不写**；有改动时逐记录
  重建——未改动块**原样复用原始压缩流字节**，改动块重新量化+压缩（内部先回读比对），
  记录重排扇区链并回写 ACCESSDB 的 **BG section（0..7）**，SCR/CBD/VOC 等 section
  一律不碰（不干扰 scn.py）。记录超 0x80000 直接报错。
- 量化策略（按需求实现，方法参考 gim 工具）：先数唯一色（透明不算），
  **≤256 无损建表，>256 才 Wu 量化**（ImageSharp WuQuantizer + 
  `ExtensivePixelSamplingStrategy` 全量采样 + 无抖动 + 透明像素固定索引 0
  + alpha 参与量化）。
- 文件分工（适配其他游戏只动第一个）：
  - `GameTables.cs` ★ 全部游戏常量：FDB section 布局、档案表（目录/前缀/槽位/section）、
    块与部件偏移、swizzle、LZSS 参数。
  - `Lz1.cs` 解码 + 正确编码器（贪心+哈希链；字面量攒 8..70 出串）。
  - `AccessDb.cs` FDB 目录表读写。
  - `BgImage.cs` 块↔像素、调色板 swizzle/半程 alpha、量化。
  - `BgArchive.cs` 解包/打包编排、list.xml。
  - `Program.cs` CLI（异常会打印堆栈，方便排障）。

构建：`tools/KitaAccess/build.bat`（或 `dotnet build -c Release`）。

## 6. 已知坑（血泪史，改代码前先读）

1. **长匹配距离上限是 1023 不是 1024**：距离域只有 10 位；写入 1024 回读变 0，
   游戏会跳过该操作导致解码错位（当年 selftest 全红就是这个）。
2. **字面量串最长 70**：`(t&0x3F)+8`，t=0xFF 是结束符，71 长度的串会写成 0xFF。
3. **控制字节在每组 8 个操作的数据之前**，不是之后（织入顺序错了整条流全错）。
4. **长匹配直接距离、短匹配距离-1**，两者不要统一。
5. 旧 bg.py 的 `compress_1bin_body` 是另一套 LZSS 编码（258-len + 距离字节），
   与本游戏解码器**完全不兼容**，从未能用；打包请一律走 KitaAccess。
6. 部件头是 GIF 包模板，**宽高字段不可改**（游戏按头上传 VRAM），工具强制 PNG
   尺寸一致。
7. BG200 记录 #542 是废数据（表项随机），解析失败原样拷贝，不要试图"修复"。

## 8. decode2r / tit_bg.p2x / mvepic / sysdat 图像（2026-08-29 深入）

### decode2r —— 第二种 LZSS（0x136FE0 入队 / 0x137090 泵 / 0x1371F0 核心 / 0x136FC0 ini）

控制字节 8 个标志位，**MSB 在前**；0=字面量；1=按 token 高 3 位分派：

| token 范围 | 语义 |
|---|---|
| 0x00-0x1F | 短匹配 len=(t>>4)+2 (2..3)，dist=(t&0xF)+1 (1..16) |
| 0x20-0x3F | RLE 填充 count=t>>4 (2..3)，值=(t&0xF)\|(t&0xF)<<4（值内嵌） |
| 0x40-0x5F | RLE 填充 count=t-61 (3..34)，值=下一字节 |
| 0x60-0x7F | RLE 填充 count=((t&0x1F)<<8\|b1)+3 (3..8228)，值=b2 |
| 0x80-0x9F | 匹配 len=(b&0xF)+3 (3..18)，dist=(16*(t&0x1F)\|(b>>4))+1 (1..512) |
| 0xA0-0xBF | 匹配 len=((b&0xF)<<8\|b2)+3 (3..4103)，dist 同上 |
| 0xC0-0xDF | 字面量串 count=t-183 (9..40) |
| 0xE0-0xFF | 字面量串 count=((t&0x1F)<<8\|b)+9 (9..8200)；t=0xE0,b=0 为**结束** |

参考实现：research/decode2r.py。注意距离公式是 `16*(t&0x1F)|(b>>4)`（<<4 不是 <<8）。
yTitle(0x15D9B0) 在 fload(tit_bg.p2x → 0x1300000) 后调用 decode2r_ini + 一串 decode2r 任务。
